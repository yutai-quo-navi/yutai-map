# 期限DBの運用

原本は `data/expiry_master.csv`。`tools/build_expiry.py` で表示用 `data/expiry.json` とX初稿を生成する。店舗DB・Cloudflareには期限データを追加しない。

## CSV列仕様

UTF-8（BOM付きも可）。1行は「年 × 会社 × 優待 × 対象発行回 × 期限種別」。列名・順序は固定。カンマ・改行を含む値はCSVの引用符で囲む。

|列|内容・書式|
|---|---|
|id|行の固定ID。英小文字・数字・`-`・`_`。訂正時も変更しない|
|code|証券コード。文字列、英字コード対応|
|company_name|会社名|
|benefit_name|優待名称。券種が違えば別行|
|issue|対象の権利回・付与回・発行回。例：2025年12月権利分。提供情報の登録時は省略可|
|expiry_date|期限日 `YYYY-MM-DD`。月しか不明なら空欄。月末を勝手に補完しない|
|research_month|調査対象月 `YYYY-MM`。期限日が確定していれば、その年月と一致させる|
|expiry_type|利用期限 / 申込期限 / 登録期限 / 予約期限 / ポイント失効 / 交換期限 / 受取期限|
|category|`dining` 外食・飲食 / `shopping` 買物・割引 / `leisure` サービス・レジャー / `catalog` カタログ・申込 / `other` その他|
|brands|利用可能ブランド。複数は `ガスト\|バーミヤン` のように縦棒区切り|
|source_url|期限・対象券の根拠になる公式ページまたはPDF。公式ページの存在だけではconfirmedにしない|
|secondary_source_url|二次情報URL。secondaryの場合必須|
|checked_on|確認日 `YYYY-MM-DD`。ユーザー承認日も記録する|
|status|`confirmed` 確認済み（公式またはユーザー承認） / `secondary` 二次情報のみ / `checking` 要確認|
|notes|券の利用制限、申込時刻、必着・消印、訂正理由など|
|issuer_id|既存店舗検索の会社ID。未対応なら空欄。証券コードと一致必須|
|search_brand|検索を特定の1ブランドに絞る場合の既存ブランド名。空欄なら会社の全ブランド|
|emoji|X初稿の行頭絵文字。空欄は🎁|
|verification_method|`official` 公式照合 / `user` 提供情報の承認。confirmedの場合必須|

## 編集・反映

普段は「7412 アトムは2026年12月まで」「2027年分は11月末まで」のようにChatGPTに渡せばよい。年だけは省略しない。出典・発行回は後から追記できる。

入力補助コマンドは証券コードと年月だけで既存行を訂正し、JSONまで同時に更新する。

```sh
python tools/edit_expiry.py --code 7412 --month 2026-12
python tools/edit_expiry.py --code 7412 --date 2026-12-31
python tools/edit_expiry.py --code 7412 --month 2027-11
```

- 同年の既存情報は同じidで訂正する。別年分は必ず新しい行を追加する。
- 同年に複数の券がある場合だけ `--id` で対象を指定する。別の券を追加する場合は `--new`。
- 初めての会社だけ `--company 会社名` を指定する。券名・種別・カテゴリ・出典は任意指定。
- 通常入力は提供情報確認済み（`confirmed` / `user`）として扱う。確認待ちにしたい場合は `--status checking`。
- 年月だけなら期限日を空欄にし、月末を勝手に補完しない。月情報として公開・X初稿に使い、日数表示は具体的な日付があるときだけ行う。
- 年の書式は `YYYY-MM` または `YYYY-MM-DD` を必須とし、JSONにも `expiry_year` を自動付与する。前年情報を翌年の期限として自動コピーしない。

公式URLまで確認した場合は `verification_method=official` にする。この場合のみ期限日・対象発行回・公式URLを必須とする。確認状態と確認経路を分けることで、ユーザーが確認済みの情報を追加の資料探しなしで反映できる。

ChatGPTで編集する場合は以下を実行し、CSVとJSONを同じコミットで更新する。

```sh
python tools/build_expiry.py
python tools/build_expiry.py --check
```

GitHub上でCSVだけ編集してmainへ反映した場合も、`Build expiry ledger and X drafts` が検証・JSON生成・コミットを行い、GitHub Pagesの再構築をリクエストする。ワークフロー失敗時はActionsから原因を確認する（不正行を黙って落として公開しない）。PRでは公開を行わず生成と検証だけを行う。

自動生成のJSONには **confirmedの全年度データ** を保持する。画面は日本時間の今月を選び、期限終了した同月分は「期限終了」と表示する。未確認行は画面にもX初稿にも出さない。行の削除は旧CSVとの照合でCIが拒否する。

## 店舗検索への接続

「お店を探す / 🔥 今月期限」を切り替える。確認済みカードに期限種別・対象発行回・公式情報・確認日を表示する。

公開済みの店舗検索会社に対応する場合、未失効または期限月確認済みのカードに「この優待が使える店を探す」を表示する。押すと会社選択・ブランド選択・店舗カテゴリを更新し、既に指定した検索地点があれば検索する。地点がなければ指定を促す。ボタンだけで現在地を取得しない。

未対応会社は公式リンクを表示する。公開前の開発会社を一般ユーザーに開放しない。指定ブランドが現行カタログに存在しない場合は会社全体へ戻る。

日数は日本時間の暦日差：7日以内⚠️、3日以内🔥、当日🚨 本日まで。サイトを開いたまま日本時間の日付が変わった場合も更新する。時刻指定や必着条件は備考に明記し、券面・公式で確認できるようにする。

## X用初稿

```sh
python tools/build_expiry.py --month 2026-09 --draft /tmp/x-expiry.txt
python tools/build_expiry.py --month 2026-09 --month-end --draft /tmp/x-month-end.txt
```

初稿はカテゴリごとに会社コード・会社名・優待名称・具体的な日付・期限種別・発行回を出力する。全月版で月末と中途日を混同しない。「明後日には紙切れ」等の表現は投稿日と券種を見て人間が加える。自動投稿は行わない。

Actionsの `Run workflow` で対象月を指定すると、`expiry-drafts` にX初稿（全月版・月末版）と前年同月の候補CSVをダウンロードできる。

## 前年同月を調査候補にする

```sh
python tools/build_expiry.py --month 2027-09 --candidates /tmp/prior-year.csv
```

confirmed以外も含め、前年の調査対象月から候補を抽出する。前年の期限を翌年に自動コピーしたり、翌年の確認済み情報として扱ったりしない。
